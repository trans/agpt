## 15:26 - Context Alpha Gate

Implemented a context-conditioned residual gate:

```text
alpha(c) = alpha_max * sigmoid(phi . features(c))
logits   = log q_tree(c) + alpha(c) * residual_logits(c)
```

The default `alpha_max` is `2 * prior_residual_scale`, and the gate weights are
zero-initialized. With `prior_residual_scale=0.10`, the initial alpha is exactly
`0.10`, matching the previous fixed-alpha setup.

Fair carved split partial run:

```text
run: carved_context_alpha_scale010_l2_002_d64_e3
prior only: 3.859, mean alpha 0.100
epoch 1:    3.811, mean alpha 0.148
epoch 2:    3.820, mean alpha 0.148
```

The epoch-1 result is a slight new best over fixed alpha. More importantly,
epoch 2 is much more stable than the fixed-alpha `L2=0.02` run, which drifted
to `3.868`.

Scaling note: the first context-alpha run had to build a feature-row cache. That
took about `242s`, raised peak RSS to about `6GB`, and produced a `324MB` cache
for the 1M-character carved split. Future runs can reuse that cache, but
Gutenberg-scale runs need a faster and more compact prior/feature path.

The GPU improves runtime by roughly `2.3x-2.8x`, but the harness is still

avoid dense per-position prior matrices where possible.

## 17:07 - Raw Memory And No Terminal Aux


This reduced optimizer steps but made learning much worse, so update count is

```text
memory_record=written

epoch 1: 3.796, ~2869 tok/s

```

Using raw memory records helped more:

```text
memory_record=raw
terminal_record_aux_weight=0.0
epoch 1: 3.794, ~3781 tok/s
epoch 2: 3.776, ~3704 tok/s
```

Interpretation: the record writer and terminal auxiliary are not helping this
count-prior residual line. They slow the harness and appear to regularize the
wrong target. The current best practical configuration is:

```text
count prior: frozen depth 8, entropy_delta + suffix_stats
residual gate: context alpha, alpha_max = 2 * residual_scale
residual scale/L2: 0.10 / 0.02
memory_record: raw
terminal_record_aux_weight: 0.0
segments_per_update: 64
```

## 19:18 - Update Frequency Sweep

Tested smaller `segments_per_update` values with the current best raw-memory,
no-terminal-aux configuration.

```text

```

Sweep:

```text
segments_per_update=32
updates/epoch: 3555
epoch 1: 3.797, ~3744 tok/s

segments_per_update=16
updates/epoch: 7110
epoch 1: 3.839, ~4040 tok/s
```

Interpretation: update frequency matters, but more frequent updates are not
automatically better. `spu=32` is close but does not beat `spu=64`; `spu=16`
is fastest but over-updates/noisier and loses quality. Keep `spu=64` as the
default for this line.
